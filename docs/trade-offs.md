# Архитектурные решения и trade-offs

[Главная](../README.md) · [Документация](README.md) · [Архитектура](architecture.md) · [Lifecycle](lifecycle.md)

При рефакторинге я оценивал пользу каждого решения, сложность реализации
и ограничения, которые оно добавляет. Эта страница фиксирует принятые мной
решения и их последствия в текущем коде.

<a id="history"></a>

## История проектирования воркеров и идемпотентности

1. **Очередь и stateless.** Я выбрал PostgreSQL для хранения джоб и координации
   воркеров через `FOR UPDATE SKIP LOCKED`. HTTP и воркеры остались в одном
   процессе, а состояние обработки — в БД: задачу может продолжить любая реплика.

2. **Границы транзакций.** Я рассмотрел блокировку джобы на всё время запроса
   провайдера, но оценил стоимость занятого соединения и долгой транзакции.
   Выбрал короткий claim → HTTP без транзакции → отдельный complete/retry;
   Job и Quote сохраняются атомарно.

3. **Упрощение владения.** Первоначально использовались UUID `LeaseToken` и
   отдельный `JobUpdate`. Я рассмотрел общую версию Job, затем выбрал уже
   существующий `Attempts` как номер захвата и `Save(ctx, job, expectedAttempt)` стал чище.
   Проверки статуса и попытки защищают от старого воркера. Lease сохранил,
   поскольку номер попытки не позволяет определить, что процесс завис.

   Прежний вариант: фрагменты `domain.Job`, отдельная структура `JobUpdate`
   из usecase и контракт сохранения. Показаны поля, относящиеся к владению:

   ```go
   type Job struct {
       ID         JobID
       Status     JobStatus
       Attempts   int
       LeaseToken uuid.UUID
   }

   type JobUpdate struct {
       ExpectedLeaseToken uuid.UUID
       LeaseUntil         time.Time
       NextAttemptAt      time.Time
   }

   type JobUpdater interface {
       Save(context.Context, *domain.Job, JobUpdate) error
   }
   ```

   Текущий вариант: сроки перенесены в [Job](../internal/domain/job.go),
   а [контракт сохранения](../internal/usecase/claim.go) принимает номер попытки:

   ```go
   type Job struct {
       ID            JobID
       Status        JobStatus
       Attempts      int
       LeaseUntil    time.Time
       NextAttemptAt time.Time
   }

   type JobUpdater interface {
       Save(ctx context.Context, job *domain.Job, expectedAttempt int) error
   }
   ```

   Раньше состояние джобы, сроки и ожидаемый токен передавались раздельно.
   Теперь `Save` получает состояние из Job, а `expectedAttempt` задаёт
   условие конкурентной записи; отдельная структура обновления больше не нужна.

4. **Восстановление и остановка.** Я оставил reclaim после lease, retry с backoff
   и отделил остановку polling от отмены активных операций. Shutdown даёт им
   время завершиться, затем отменяет по deadline и ждёт воркеры перед cleanup.
   Цена коротких транзакций — возможный повтор запроса провайдера после сбоя
   и пересечение попыток после lease; гарантируется защита записи результата.

5. **Первая идемпотентность.** Ключ находился в Job и usecase. Повтор возвращал
   существующую джобу с текущим статусом и HTTP 200; другая пара давала конфликт.
   Я пересмотрел этот контракт: повтор доставки должен воспроизводить исходный
   ответ, а актуальное состояние задачи клиент получает отдельным GET.

6. **Сохранённый HTTP-ответ.** Я перенёс ключ в middleware и отдельную таблицу
   `http_idempotency`. Создание Job и сохранение ответа объединены одним commit;
   конкурентные запросы с ключом сериализуются в БД. Повтор получает исходный
   202 и тело без вызова usecase, `X-Request-ID` остаётся текущим, ошибки
   не сохраняются. Цена — новое тело с тем же ключом игнорируется;
   ключи глобальны, TTL и очистка не реализованы.

HTTP-идемпотентность и владение попыткой решают разные задачи: повтор POST
не создаёт новую джобу, но не гарантирует единственный запрос к провайдеру
при любых сбоях. Подробности: [HTTP-идемпотентность](idempotency.md),
[обработка джоб](jobs.md) и [границы гарантий](reliability.md#guarantees).

## Принятые решения после Рефакторинга

| Решение | Польза | Цена решения |
| --- | --- | --- |
| Один HTTP-сервис после удаления gateway, gRPC и генерации | Меньше процессов, контрактов и инструментов сборки; handler сразу вызывает usecase | Публичный gRPC-контракт больше не поддерживается; внешний клиент работает через HTTP |
| Прагматичный DDD и clean-подход без лишних абстракций | Явные границы бизнес-правил, сценариев и инфраструктуры | Границы требуют дисциплины и тестов; архитектура не запрещает каждое нарушение автоматически |
| Домен в двух файлах: Job и Quote, отдельные типы ID, без getters | Компактные модели, типизированные идентификаторы, переходы статусов рядом с сущностью | Открытые поля технически можно изменить напрямую, обойдя доменные методы |
| Допустимые переходы статусов в Job | Сценарии не присваивают бизнес-статусы произвольно | Новый переход требует изменения домена и тестов, а не только SQL или handler |
| Список валют задаётся конфигурацией | Новые валюты допускаются без перекомпиляции домена | Допуск сервиса и поддержка валюты источником — разные проверки |
| Usecase по функциям, а не по Job/Quote | Каждый файл описывает действие, например GetLatest или CompleteJob | Некоторые сценарии используют оба repo; вспомогательные операции разделяют узкие контракты |
| Ресурсный провайдер с HTTP-клиентом, middleware, внешними моделями и ACL | Frankfurter изолирован, его JSON не проникает в домен | Несколько небольших файлов и конвертация нужны даже для простого endpoint |
| Интерфейсы объявляются по месту использования | Потребитель задаёт минимально нужный контракт | В разных потребителях могут встречаться похожие небольшие интерфейсы |
| Композиция и управление процессом в internal/app | main остаётся точкой входа, startup/shutdown можно тестировать отдельно | App намеренно знает конкретные адаптеры и становится местом их подключения |
| Один [Dockerfile](../deploy/Dockerfile) с targets `currency-service` и `migrate` | Общая сборка двух команд и отдельный запуск миграций | SQL встроен в migrator: после его изменения образ нужно пересобрать; миграции не выполняет сервис |

Я поставил Recoverer первым в цепочке middleware, затем request ID,
логирование, timeout и ограничение тела. ErrorHandler обрабатывает ошибки
handler. См. [цепочку и контекст](architecture.md#context).

## Компромиссы текущей реализации

### Общая инфраструктура в pkg

Я вынес создание пула, менеджер транзакций, HTTP client/server и общие
middleware в `pkg`. SQL, маршруты, формат ошибок и внешний контракт Frankfurter
остаются в `internal`. Пакеты `pkg` не импортируют `internal`; заголовки
провайдера и callback Recoverer передаются при сборке приложения.

Цена — параметры общей инфраструктуры задаются отдельно от настроек
конкретного адаптера. HTTP server остаётся стандартным `*http.Server`,
а управление общим shutdown HTTP и воркеров остаётся в app.
[Границы слоёв](architecture.md#boundaries), [lifecycle](lifecycle.md#ownership).

### HTTP и воркеры в одном процессе

Я объединил HTTP и воркеры в одном процессе `currency-service`.
Так проще запуск, общие настройки и владение ресурсами. Цена — общий цикл
жизни: ошибка HTTP Serve останавливает всё приложение, а нагрузка API и
воркеров делит пул БД и ресурсы процесса.

Сейчас `WORKER_COUNT` регулирует параллельность внутри процесса. При
потребности независимо масштабировать API и обработку можно оставить те же
сценарии и repo, но разделить точки запуска. На текущем этапе я выбрал
общий процесс ради простоты запуска. [Lifecycle](lifecycle.md), [композиция](../internal/app/app.go).

### PostgreSQL одновременно хранит данные и очередь

Я выбрал PostgreSQL для хранения данных и очереди задач. `quote_jobs` и
`FOR UPDATE SKIP LOCKED` позволяют обойтись без отдельного брокера.
Приём запроса, ключ идемпотентности и результат живут в одной БД.
Цена — polling, SQL-блокировки и конкуренция с API за соединения; нет
отдельного механизма push-доставки задач или управления брокером.

При выборе я учитывал простоту инфраструктуры для текущего сервиса.
Повод пересмотреть это решение — измеримая нагрузка polling/блокировок
или требования к независимой доставке.
[Обработка и конкуренция](jobs.md#lease).

### Транзакция скрыта за менеджером и контекстом

Я выбрал менеджер транзакций и передачу tx через контекст, чтобы сценарии
не зависели от pgx. Usecase задаёт границу `WithinTransaction`, repo извлекает
общий `pgx.Tx` через accessor из `pkg/postgres` и приватный ключ `txCtx`.
Это сохраняет простой интерфейс двух repo. Цена — транзакционная зависимость не видна в каждой
сигнатуре: модификация без нужного контекста обнаруживается во время выполнения.

При существующем tx менеджер использует его без отдельного begin/commit;
завершает транзакцию внешняя операция. Ошибка внутренней операции должна
дойти до внешнего callback, чтобы тот выполнил rollback.
Состояние для сохранения находится в `Job`,
ожидаемый номер попытки передаётся отдельным аргументом Save. Репозиторий
не импортирует usecase. Я счёл менеджер транзакций достаточным для одного
SQL-адаптера; отдельный unit-of-work с объектами repo на каждую транзакцию
добавил бы ещё один механизм управления зависимостями.
[Менеджер транзакций](../pkg/postgres/transaction.go),
[контракт транзакций](../internal/usecase/transaction.go),
[контракт сохранения джобы](../internal/usecase/claim.go).

### Короткие claim/complete вместо транзакции вокруг сети

Я разделил обработку на короткие транзакции claim и complete, чтобы
освободить соединение и блокировку БД на время сети.
Claim сохраняет владение и делает commit, затем вызывается Frankfurter,
после чего отдельная транзакция сохраняет Quote и статус Job.
Цена — процесс может упасть между запросом
источника и сохранением результата; после lease запрос повторится.

Номер попытки, блокировка строки и уникальный индекс защищают сохранение
результата, но exactly-once внешний вызов не обещается. Этот компромисс
позволяет восстанавливать джобы без длинных транзакций и распределённого
протокола. [Последовательность обработки](jobs.md#processing).

### Lease с номером попытки вместо отдельного токена и heartbeat

Я использовал номер попытки для защиты владения и сохранил lease для
восстановления зависших задач. Start/Reclaim увеличивают `Attempts`;
complete/retry передают полученный номер как `expectedAttempt`.
Он заменяет отдельный UUID-токен. Цена —
`Attempts` нельзя сбрасывать или уменьшать в течение жизни джобы; это номер
попытки, а не универсальная версия любых изменений сущности. Срок аренды
сохраняется в `Job.LeaseUntil`, backoff — в `Job.NextAttemptAt`.

Если запрос и complete заняли больше lease, другой воркер может сделать
повторный вызов источника. Номер прежней попытки после reclaim уже не подходит.
Параллельные внешние запросы при истечении аренды остаются возможными;
номер попытки защищает сохранение результата.

Lease должен быть больше provider timeout с запасом для БД. Проверка
конфига требует только строгого неравенства, весь запас выбирается настройкой.
Истечение срока без новой попытки само по себе не запрещает complete.
[Lease](jobs.md#lease), [таймауты](configuration.md#variables).

### Retry на уровне сценария

Я оставил повторы и backoff на уровне сценария джобы. HTTP-клиент
не добавляет свой цикл retry.
Так видно число начатых попыток и время следующего запуска, без умножения
попыток на двух уровнях. Цена — даже протокольная ошибка источника сейчас
попадает в ту же retry-политику, что и сетевой сбой; классификация
постоянных и временных ошибок не детализирована.

По умолчанию используется exponential backoff без jitter. Разделение ошибок
и jitter стоит добавить при конкретной необходимости управлять нагрузкой
или не повторять заведомо бесполезные запросы. [Retry](jobs.md#retry).

### Простые модели с доменными методами

Я оставил Job и Quote в двух файлах с открытыми полями, конструкторами и
доменными методами. Это сохраняет компактность моделей и размещает правила
рядом с сущностями. Цена — код должен обращаться к переходам
через методы, а восстановление из БД не прогоняет конструктор новой сущности.

Отдельные типы JobID/QuoteID предотвращают смешение ID в типизированных
сигнатурах, но не превращают модель в полностью закрытый объект. Более
строгая инкапсуляция оправдана, если появятся реальные нарушения инвариантов.
[Домен](domain.md).

### Контекст для технических данных, input для бизнес-входа

Я рассматривал передачу данных джобы через middleware context, затем выбрал
явные входные структуры для пары и ID задачи. В контексте остаются request ID,
отмена/deadline, tx PostgreSQL и ключ HTTP-идемпотентности.
Технический ключ обрабатывает middleware.

Это делает зависимости сценария видимыми в сигнатуре и исключает загрузку
бизнес-данных middleware. Цена — нужны небольшие входные структуры и
конвертеры. Request ID из HTTP не сохраняется в джобе и не переносится
автоматически в отдельный worker context; сквозная трассировка фоновой
обработки не реализована. [Конвертеры](architecture.md#converters).

### Frankfurter за ACL

Я выбрал Frankfurter и изолировал его контракт за ACL. Сценарию достаточно
decimal и времени источника; API интегрирован обычным HTTP-клиентом без SDK.
Цена — доступность и поддерживаемые валюты зависят от источника, а
`latest` означает последний сохранённый ответ, а не поток рыночных цен.

Менять base URL можно только на совместимый контракт. Для другой схемы
нужны новый клиент и ACL, а не просто новое значение ENV.
[Провайдер](provider.md), [latest API](api.md#latest).

### Decimal и ограниченная точность PostgreSQL

Я выбрал decimal для курса, чтобы сохранить десятичную точность.
Цена не проходит через float64: JSON источника → decimal → строка API/SQL.
Это сохраняет десятичное значение в пределах `NUMERIC(38,18)`. Цена решения —
явные преобразования и ограничение схемы: слишком большое значение не
сохранится, лишняя дробная точность ограничена масштабом БД.

Домен проверяет положительность, а не диапазон конкретной БД. При ошибке
записи complete откатывает и Job, и Quote. [Модель Quote](domain.md#quote).

### Допуск валют отдельно от завершения принятой джобы

Я ограничил проверку `ALLOWED_CURRENCIES` новыми запросами и latest,
чтобы изменение конфига сохраняло возможность завершить принятые задачи.
Complete использует сохранённую пару джобы.
Цена — результаты по исключённой паре доступны через
job ID, latest проходит новый допуск. Повтор POST с уже сохранённым ключом
возвращает исходный ответ до повторной бизнес-валидации.

Конфиг не доказывает поддержку кода источником; у принятой джобы возможен
retry/fail. [Валюты](configuration.md#currencies), [идемпотентность](api.md#idempotency).

### Сохранённый HTTP-ответ для идемпотентности

Я вынес ключ из Job и usecase в middleware и `http_idempotency`, чтобы
идемпотентность отвечала за воспроизведение HTTP-ответа.
Job и успешный HTTP-ответ сохраняются одной транзакцией; конкурентные
запросы с одним ключом ждут её завершения. Повтор возвращает исходный 202
и тело, а актуальный статус читается через GET.

Цена — тело нового запроса с тем же ключом не проверяется и не создаёт
новую операцию. Клиент должен выделять новый ключ для другого действия.
Ошибки не сохраняются, TTL и очистка не реализованы. Транзакция охватывает
разбор тела, создание Job и сериализацию ответа, но не запрос провайдера.
[Механизм и границы](idempotency.md).

### Drain активных операций перед закрытием ресурсов

Я отделил остановку опроса от отмены активного worker context. Это даёт
текущей джобе шанс закончить HTTP и complete после SIGTERM. Цена — процесс
не останавливается мгновенно; по дедлайну отменённая джоба может ждать lease
до восстановления следующим процессом.

HTTP и воркеры делят один shutdown budget. После отмены приложение всё ещё
ждёт выхода воркеров, полагаясь на контекстные клиент и pgx; Docker задаёт
внешнюю границу SIGKILL. [Lifecycle и его границы](lifecycle.md#limits).
