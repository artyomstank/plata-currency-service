# HTTP-идемпотентность

[Главная](../README.md) · [Документация](README.md) · [API](api.md#idempotency) · [Архитектура](architecture.md#context)

Идемпотентность относится к доставке HTTP-запроса. Доменная Job и
RequestUpdate не знают ключ, заголовки или формат сохранённого ответа.

Связь с обработкой джоб, stateless и история доработок описаны в
[общем документе о надёжности](reliability.md).

<a id="contract"></a>

## Контракт

`POST /v1/quote-updates` принимает необязательный `Idempotency-Key` до 128 байт.
Ключ должен быть корректным UTF-8 без нулевого символа; он не нормализуется.
Пустое значение считается отсутствующим. Без ключа каждый успешный запрос
создаёт новую Job. С ключом первый успешный запрос
сохраняет HTTP-статус, тело и заголовки в PostgreSQL.

Следующий запрос с тем же ключом получает тот же 202 и то же тело, даже если
Job уже done/failed или новое тело отличается. JSON и валютная пара повторного
запроса не разбираются. Для новой операции клиент использует новый ключ.
Актуальный статус и котировка читаются через GET по исходному jobId.

`X-Request-ID` определяется текущим запросом и не воспроизводится из таблицы.
Сохраняются только успешные ответы 2xx; ошибки оставляют ключ свободным
для исправленного запроса или повтора после сбоя.

<a id="transaction"></a>

## Одна транзакция для Job и HTTP-ответа

Цепочка POST: Recoverer → RequestID → Logger → Timeout → BodyLimit →
Idempotency → ErrorHandler.Adapt → handler → RequestUpdate.

1. Middleware проверяет технический ключ и помещает его в context.
2. Менеджер транзакций открывает tx; repo пытается вставить ключ с `ON CONFLICT DO NOTHING` и читает строку `FOR UPDATE`.
3. Если ответ уже сохранён, middleware возвращает его без handler/usecase.
4. Иначе handler декодирует JSON и вызывает RequestUpdate. Его `WithinTransaction` использует существующий tx; Job создаётся через доменный конструктор и repo.
5. Статус, заголовки и тело HTTP-ответа записываются в буфер и затем в `http_idempotency` через тот же tx.
6. После commit middleware отправляет ответ клиенту. Ошибка, panic или отмена до commit откатывает Job и ключ вместе.

Ошибка самого commit может оставить результат неизвестным для клиента:
PostgreSQL мог применить транзакцию до потери соединения. Повтор с тем же
ключом прочитает сохранённый ответ, если commit состоялся, либо выполнит
операцию заново, если изменений в БД нет.

При двух репликах запрос с тем же ключом ждёт уникальный индекс PostgreSQL:
после commit первого он читает сохранённый ответ; после rollback может
сам выполнить операцию. Проверки «найти ключ, потом создать Job» без
сериализации нет. Память процесса не является источником состояния.

Вызов Frankfurter выполняет отдельный воркер после commit. Транзакция
идемпотентности не удерживается на время запроса к провайдеру.

## Таблица и перенос существующих ключей

`http_idempotency` содержит `key`, `status_code`, `response_headers` JSONB,
`response_body` BYTEA и `created_at`. BYTEA сохраняет исходные байты JSON,
а не повторно сериализованный объект. Строка без ответа существует только
в незавершённой транзакции первого запроса; при ошибке она откатывается.

Миграция [0004](../migrations/0004_http_idempotency.up.sql) переносит ключи
из `quote_jobs`, восстанавливая исходный ответ создания 202 с jobId и pending.
Прежняя версия не хранила HTTP-ответы, поэтому перенос восстанавливает
известный формат ответа создания, а не историю изменявшихся ответов POST.
После переноса колонка ключа удаляется из таблицы джоб.

Перед применением остановите старые экземпляры сервиса. Старый код ожидает
колонку в `quote_jobs`, новый — отдельную таблицу. [Обратная миграция](../migrations/0004_http_idempotency.down.sql)
возвращает ключи существующим Job по jobId из сохранённых ответов и удаляет
таблицу HTTP-ответов. Применение описано в [разработке](development.md#migrations).

<a id="limits"></a>

## Границы

- Ключи глобальны для единственного защищённого POST-маршрута; пользовательский scope и TTL не реализованы.
- Повтор не сравнивает тело запроса. Для другого действия требуется другой ключ.
- Ожидание конкурентного запроса ограничено HTTP deadline; при timeout клиент может повторить запрос позже.
- Middleware буферизует небольшой JSON-ответ; streaming и передачу больших ответов этот маршрут не использует.
- Ошибка отправки после commit не отменяет Job: повтор с тем же ключом вернёт сохранённый ответ.
- HTTP-идемпотентность не меняет lease/Attempts воркеров и не обещает единственный внешний вызов провайдера после сбоя.
